# v1.21.6 — MCP 协议错误不再报废整回合

发布日期：2026-09-21。

本版一个主题：**MCP 工具的协议错误必须作为 tool 结果回给模型自纠，而不是裸抛异常炸掉整回合**。
修复由真实生产事故驱动（Pencil 桌面 App 关掉文档后，连续两个回合报废、失败调用丢失），
与 v1.20.1 的「工具超时杀回合」同构——防线按异常类型白名单兜底，每种新异常类型就是一个新洞；
本版把「MCP 工具执行」这个整类来源在离异常最近的地方焊死。

## 事故现场（2026-09-21，session 20260921T051342）

时间线（生产日志与 会话 events 对照）：

| 时间 | 事件 |
| --- | --- |
| 15:48 | Pencil 文档 `pencil-new.pen` 还开着，`get_app_state` 调用成功 |
| 15:48–16:15 | 文档窗口在 Pen.app 里被关闭（App 未退出） |
| 16:15:59 | 模型调 `read-skill` → JSON-RPC `-32603` `Failed to access file "". A file needs to be open in the editor`，**回合 3 报废** |
| 16:16:42 | 用户问「怎么出错了？」——但错误原因谁也没看到 |
| 16:16:55 | 模型重试 `get-app-state` → 同样报错（`file "undefined"`），**回合 4 报废** |

讽刺的是这是一条**本可自行消解**的错误：模型只要看到「A file needs to be open in the editor」，
就会提示用户打开文件或改走别的工作；但回合直接崩掉，模型与用户都没有机会看到原因。
另两次失败的 MCP 调用**均未落盘**进会话 events（回合失败路径裁掉了悬空 tool_calls），
`-c` 恢复会话时这段上下文整体缺失。

## 根因

MCP server 返回 JSON-RPC error 时，Spring AI 的 `SyncMcpToolCallback` 打完 ERROR 日志后
**裸抛 `McpError`**——不包装成 `ToolExecutionException`。于是两道既有工具容错防线全部绕过：

- `DefaultToolCallingManager` 只把 `ToolExecutionException` 交给
  `ResilientToolExecutionExceptionProcessor`（转错误文本回模型）；
- `ResilientToolCallingManager` 只兜「No ToolCallback found」的 `IllegalStateException`
  （工具名拼错）。

异常沿 advisor 链一路上抛，`CodingAgent.handleError` 把整回合标成失败。与 v1.20.1 修过的
Brave 搜索超时事故完全同构：那次是超时包装器抛 `IllegalStateException` 绕过兜底，这次换成
MCP 回调裸抛 `McpError`。教训一致：**按异常类型白名单兜底，每种新类型就是一个新洞**。

## 修复

新增 `ResilientMcpToolCallback` 装饰器，在 `McpRegistry.decorate` 装配链接入：

```
PermissionCallback → ResilientMcpToolCallback → ToolEventCallback → 媒体外置 → 真实工具
```

- **catch `RuntimeException` 转错误文本返回**（点名工具 + 异常类型 + 消息 + cause 链，
  链尾根因优先；单行，不附堆栈——MCP 协议错误的本地堆栈全是 reactor/SDK 传输帧，对模型
  零信息量，只烧 token）。不按类型列举：按类型列举就是重蹈白名单覆辙，SDK 升级换异常
  类型、传输层超时包装都会再出新洞。
- **`Error` 穿透不吞**：OOM 等 JVM 级故障不属于「工具执行失败」，吞掉会掩盖致命问题。
- **装配位置**：`ToolEventCallback` 之外（失败先被记成 `ok=false`，TUI 保留 ✗ 不误报成功，
  再被转成错误文本）、`PermissionCallback` 之内（权限拒绝不经它，语义不变）。

### 同场景重演时的行为对比

| | 修复前 | 修复后 |
| --- | --- | --- |
| TUI | `⚠ 出错`，整回合报废 | `⎿ ✗ mcp__pencil__read_skill`，回合继续 |
| 模型收到 | 什么都没有 | 错误文本（含「A file needs to be open in the editor」）→ 提示用户打开文件 |
| 会话落盘 | 失败调用丢失 | 正常落盘，`-c` 恢复不缺上下文 |

### 使用注意：Pencil（Pen.app）必须开着文档

排查本次事故时确认的 Pencil 侧行为：**桌面 App 没有打开 .pen 文档时，所有 MCP 工具调用
一律被拒**（包括 `get_app_state`、`read_skill` 这类本不需要文档的只读工具），且重开 App
不恢复上次文档。对人的使用无所谓，接 agent 干活前请先开一个文档（新建的空文档也行）。
配了本版修复后，再撞上这个场景模型会直接收到错误原文并提示你打开文件，而不是回合报废。

## 验证

- `mvn -pl springai-code-tui -am clean test`：inline-patch 75 项、code-tui 2101 项测试
  无失败、无错误（跳过 13 项为门控冒烟）。
- 新增测试：`ResilientMcpToolCallbackTest` 6 项（协议错误转文本不裸抛、成功透传、
  cause 链完整、Error 穿透、单行无堆栈、端到端——经生产堆栈里炸掉的那层
  `DefaultToolCallingManager` 验证错误成为 `ToolResponseMessage`、回合存活）、
  `McpRegistryTest` 接线用例（错误文本返回 + `ToolEventCallback` 仍记 `ok=false`）。
  RED 阶段确认 4 项用例因裸抛 `McpError` 而 ERROR（复现事故形态）后才实现。
- 发布包解包核验：主 jar 含 `ResilientMcpToolCallback.class`、版本号 1.21.6。
