# v1.21.6 — MCP 协议错误不再报废整回合 + OpenAI 系 60s 超时回归 + 图片放宽到 10 张

发布日期：2026-09-21。

本版三处修复：前两处由生产事故驱动、且同源于此前的 Spring AI 2.0.1 升级，第三处为图片与
拖图体验放宽。

1. **MCP 协议错误不再报废整回合** —— MCP server 返回 JSON-RPC error 时 `SyncMcpToolCallback`
   裸抛 `McpError`，穿透两道工具容错防线，一次工具失败即整回合报废。
2. **OpenAI 系 60s 总超时回归** —— 2.0.1 的 `OpenAiChatOptions` 默认 `timeout=PT1M` 顶掉了
   本工程的空闲超时兜底，总时长超 60 秒的流式回合被 cancel 成 `Stream failed`，且重试必挂。
3. **图片与拖图体验** —— 用户图上限 3 → 10 张、拖图在输入框显示 `[IMAGE1]` 占位符，
   并修复「拖图紧贴已有文字时识别不出」。

第 1、2 条同源：都来自 Spring AI 2.0.1 升级（提交 `7d115fa1`，为修流取消不释放连接）。
那次升级夹带了两处对行为有实质影响的变化——一处新增了没人要过的工具调用限流
（已在 [v1.21.7](https://github.com/javaside/springai-agentdemo/blob/main/docs/release-notes/v1.21.7.md) 关闭），
一处改掉了每请求超时默认值（在本版修复）。

## 一、MCP 协议错误不再报废整回合

### 事故现场（2026-09-21，session 20260921T051342）

时间线（生产日志与 会话 events 对照）：

| 时间 | 事件 |
| --- | --- |
| 15:48 | Pencil 文档 `pencil-new.pen` 还开着，`get_app_state` 调用成功 |
| 15:48–16:15 | 文档窗口在 Pen.app 里被关闭（App 未退出） |
| 16:15:59 | 模型调 `read-skill` → JSON-RPC `-32603` `Failed to access file "". A file needs to be open in the editor`，**回合 3 报废** |
| 16:16:42 | 用户问「怎么出错了？」——但错误原因谁也没看到 |
| 16:16:55 | 模型重试 `get-app-state` → 同样报错（`file "undefined"`），**回合 4 报废** |

讽刺的是这是一条**本可自行消解**的错误：模型只要看到「A file needs to be open in the editor」，
就会提示用户打开文件或改走别的工作；但回合直接崩掉，模型与用户都没有机会看到原因。
另两次失败的 MCP 调用**均未落盘**进会话 events（回合失败路径裁掉了悬空 tool_calls），
`-c` 恢复会话时这段上下文整体缺失。

### 根因

MCP server 返回 JSON-RPC error 时，Spring AI 的 `SyncMcpToolCallback` 打完 ERROR 日志后
**裸抛 `McpError`**——不包装成 `ToolExecutionException`。于是两道既有工具容错防线全部绕过：

- `DefaultToolCallingManager` 只把 `ToolExecutionException` 交给
  `ResilientToolExecutionExceptionProcessor`（转错误文本回模型）；
- `ResilientToolCallingManager` 只兜「No ToolCallback found」的 `IllegalStateException`
  （工具名拼错）。

异常沿 advisor 链一路上抛，`CodingAgent.handleError` 把整回合标成失败。与 v1.20.1 修过的
Brave 搜索超时事故完全同构：那次是超时包装器抛 `IllegalStateException` 绕过兜底，这次换成
MCP 回调裸抛 `McpError`。教训一致：**按异常类型白名单兜底，每种新类型就是一个新洞**。

### 修复

新增 `ResilientMcpToolCallback` 装饰器，在 `McpRegistry.decorate` 装配链接入：

```
PermissionCallback → ResilientMcpToolCallback → ToolEventCallback → 媒体外置 → 真实工具
```

- **catch `RuntimeException` 转错误文本返回**（点名工具 + 异常类型 + 消息 + cause 链，
  链尾根因优先；单行，不附堆栈——MCP 协议错误的本地堆栈全是 reactor/SDK 传输帧，对模型
  零信息量，只烧 token）。不按类型列举：按类型列举就是重蹈白名单覆辙，SDK 升级换异常
  类型、传输层超时包装都会再出新洞。
- **`Error` 穿透不吞**：OOM 等 JVM 级故障不属于「工具执行失败」，吞掉会掩盖致命问题。
- **装配位置**：`ToolEventCallback` 之外（失败先被记成 `ok=false`，TUI 保留 ✗ 不误报成功，
  再被转成错误文本）、`PermissionCallback` 之内（权限拒绝不经它，语义不变）。

#### 同场景重演时的行为对比

| | 修复前 | 修复后 |
| --- | --- | --- |
| TUI | `⚠ 出错`，整回合报废 | `⎿ ✗ mcp__pencil__read_skill`，回合继续 |
| 模型收到 | 什么都没有 | 错误文本（含「A file needs to be open in the editor」）→ 提示用户打开文件 |
| 会话落盘 | 失败调用丢失 | 正常落盘，`-c` 恢复不缺上下文 |

### 使用注意：Pencil（Pen.app）必须开着文档

排查本次事故时确认的 Pencil 侧行为：**桌面 App 没有打开 .pen 文档时，所有 MCP 工具调用
一律被拒**（包括 `get_app_state`、`read_skill` 这类本不需要文档的只读工具），且重开 App
不恢复上次文档。对人的使用无所谓，接 agent 干活前请先开一个文档（新建的空文档也行）。
配了本版修复后，再撞上这个场景模型会直接收到错误原文并提示你打开文件，而不是回合报废。

## 二、OpenAI 系 60s 总超时导致 `Stream failed`

### 现象

大上下文 + thinking + 长输出的流式回合，**总时长一旦超过 60 秒**就被 watchdog cancel，
报 `OpenAIIoException: Stream failed`；重试同样受这 60 秒限制，必然再次失败——表现为
整批任务全量断流（interview-drill 全量断流事故）。

### 根因

这是 **Spring AI 2.0.1 升级引入的回归**，与本版第一条同源：

`OpenAiChatOptions.builder()` 默认 `timeout = PT1M`，且**无法置回 `null`**；
`buildRequestOptions` 见非 null 就写入 `RequestOptions.timeout`，openai-java 每次
`newCall` 据此重建 OkHttp 超时——这个 `callTimeout = 60s` 是**整个调用的总时长**语义，
直接顶掉了 base client 上配好的 read / connect / write 四元组。

而本工程的空闲兜底本来就该由 `StreamIdleTimeoutChatModel` 负责——它的语义是
**「相邻两个数据块之间」的最大间隔**（默认 300 秒，可配 `CODETUI_LLM_READ_TIMEOUT_SECONDS`）。
两者语义冲突：真正该管的是「多久没有新数据」，却被换成了「整轮最多 60 秒」，
于是越需要长时间思考的回合越先被砍。

### 修复

`OpenAiTimeouts` 新增 `CHAT_OPTIONS_TOTAL_TIMEOUT = Duration.ZERO`，四家 OpenAI 系
provider（`openai` / `zhipu` / `qwen` / `opencode-go`）的 `defaultOptions`、
`options(model)`、`options(model, thinking)` 三条路径**显式携带**该值。

`ZERO` 经 `Timeout.request = 0` 映射为 OkHttp `callTimeout(0)` = 禁用总时长超时，
把时间控制权交回 `StreamIdleTimeoutChatModel`。

DeepSeek / Anthropic 没有这个默认值，不受影响。

守卫测试 `ProviderOptionsCallTimeoutGuardTest`：四家 provider × 三条路径逐一断言
`getTimeout() == ZERO`，钉死不得再回退为 `PT1M`。

## 三、图片与拖图体验

### 3.1 用户图上限 3 → 10 张

预算三处联动放宽，依据是各模型每请求张数的官方口径：Claude 直连 100 张/请求
（200k 上下文档）、Qwen-VL 硬顶 10 张（超限报 `Must be [0, 10]`）、GLM-4V-Plus 5 张、
OpenAI 无明确数字（社区实测 ~16 张）、DeepSeek 按 token 计无张数限制——**10 贴住最紧的
Qwen 硬顶**，其余家全部容得下。

| 常量 | 变更 | 理由 |
| --- | --- | --- |
| `MAX_USER_IMAGES` | 3 → 10 | 贴住最紧的 Qwen-VL 硬顶 |
| `MAX_USER_TURN_DELIVERIES` | 36 → 120 | 10 张 × 12 轮，维持原口径 |
| `MAX_REQUEST_TOKENS` | 16k → 32k | 张数放宽后 token 成了隐形瓶颈：最贵档 OpenAI 聚合网关实测无单图封顶（2048×1152 ≈ 2.8k/张），10 张 ≈ 28k，16k 时第 6 张就被拒 |

守卫测试钉住「默认上限必须容得下 10 张满档图，且仍然有界」。

### 3.2 拖图显示 `[IMAGE1]` 占位符

终端拖图即粘贴，路径太长，贴几张就糊成一片、看不出贴了什么。整段粘贴全是可识别图片路径时，
输入框只插 `[IMAGE1]`（编号递增；Finder 多选一次多张各占一号），真实路径登记进映射。

识别层展开附件行照常工作；提交正文保留占位符原文、引用块附后（模型按 name 对号）；
提交 / 清空后编号复位。

两个隐蔽边界各有回归测试：

- 展开的裸路径含空格（中文截图名几乎必带）会被分词切碎 → 展开时用双引号包裹
  （tokenize 认的三种拖拽形态之一）；
- 闭引号后紧跟文字（`[IMAGE1]看`）会粘成 `a.png看` 这个不存在的文件 → tokenize 闭引号
  即出词，引号包裹本身就是完整的词边界。

### 3.3 修复「拖图紧贴文字不识别」

终端拖图即 bracketed paste，与已有文字之间**不保证有空白**；识别器按空白切词后，
整串（文字 + 路径）变成一个不存在的路径 → 识别 0 张且无任何提示；拖第二张时才有分隔，
所以表现为「只认出第二张」。

修复：`handlePasteEvent` 检测到粘贴内容整段均为可识别图片路径（含 overflow）时，
在粘贴文本与两侧紧贴的非空白字符之间补边界空格；普通文本 / 代码粘贴原样不变。
`AttachmentLineTest` 新增回归（首拖即提示、两张计数、中间插入三种转义形态、普通粘贴不动）。
