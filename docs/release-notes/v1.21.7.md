# v1.21.7 — 工具调用不再有隐藏的次数上限

发布日期：2026-09-21。

本版一个主题：**工具调用不该有隐藏的天花板**。Spring AI 2.0.1 升级夹带进了一套回合内限流
（每工具 40 次、总量 150 次，撞限直接抛异常），它既没有被决策过、也没有出现在任何文档里，
却在一次正常的大改动任务中把整个回合打哑。本版把它**默认关掉**，并保留可配置的熔断开关——
要限，你自己说了算；限了，也只是错误文本回给模型自纠，不再杀回合。

## 问题现场

用户在 code-tui 里执行一个改动点较多的任务（数十处 Edit），模型正要继续改时，收到：

```
Tool call limit (40) exceeded for tool 'Edit'. No further calls to this tool are allowed in this turn.
```

之后**模型彻底停住不动了**——不是它不想干，是这个回合已经死了。

## 根因

该提示**不是 code-tui 的实现**，仓库源码里搜不到；顺着发行包追下去，落点是：

```
lib/spring-ai-model-2.0.1.jar
  └─ org.springframework.ai.model.tool.ToolCallLimits          ← 2.0.1 新增
  └─ org.springframework.ai.model.tool.ToolCallLimitExceededException
     "Tool call limit (%d) exceeded for tool '%s'. No further calls to this tool are allowed in this turn."
     "Total tool call limit (%d) exceeded for this turn. No further tool calls are allowed."
```

本地 m2 全量二分确认：Spring AI `1.0.0 / 1.0.1 / 1.0.3 / 1.1.0–1.1.6 / 2.0.0-M2…M7 / 2.0.0-RC1 / 2.0.0`
**都没有** `ToolCallLimits`，**只有 2.0.1 有**。它随提交 `7d115fa1`（「升级 Spring AI 2.0.1，
修复流取消不释放连接」）进入本项目——为修一个流式取消的 bug 而升级，限流是搭顺风车进来的。

框架默认值（反编译 `DefaultToolCallingManager$Builder` 构造器确认）：

| 项 | 默认值 |
| --- | --- |
| `defaultMaxCallsPerTool` | 40 |
| `maxTotalToolCalls` | 150 |
| `onLimitExceeded` | `THROW` |

而 `ToolCallLimitExceededException extends RuntimeException`——**不是** `ToolExecutionException`。
于是与本工程 v1.20.1、v1.21.6 两次事故**完全同构**的穿透再次发生，只是这次防线外的雷在框架里：

- `DefaultToolCallingManager` 只把 `ToolExecutionException` 交给
  `ResilientToolExecutionExceptionProcessor`（转错误文本回模型）；
- `ResilientToolCallingManager` 只兜「No ToolCallback found」的 `IllegalStateException`。

两道防线都被绕过，异常沿 advisor 链一路上抛，`CodingAgent.handleError` 把整回合标成失败。
**第三次白名单教训**：防线按异常类型枚举兜底，每次依赖升级、每个新异常类型都是一个新洞。

### 子 agent 同样中招

`SubagentRunner.execute` 原本依赖 `ChatClient.builder(model)` **自动注册**的 `ToolCallingAdvisor`，
其 manager 是框架裸默认——同样 40/150/THROW，且**完全没有**本工程的 Resilient 容错。
主 agent 有的两道防线它一道也没有。

## 修复

新增 `TurnToolLimitWiring`：主 agent 与子 agent **同源**共用的 `ToolCallingManager` 工厂
（`SubagentRunner` 自己的教义——「模型、工具集、系统提示、重试策略全部同源，否则两条路会
各自漂移，而『后台任务的行为和前台不一样』是最难排查的那类缺陷」）。

策略：

- **默认不限**——`unlimitedCallsPerTool()` + `unlimitedTotalToolCalls()`，框架那套 40/150/THROW
  被整个关掉。自主性优先：大任务不该被一个没人决策过的数字拦腰截断。
- **可配置**——需要熔断时用环境变量：
  | 变量 | 含义 |
  | --- | --- |
  | `CODETUI_MAX_CALLS_PER_TOOL` | 回合内单工具调用上限（如 Edit 连续调用次数） |
  | `CODETUI_MAX_TOTAL_TOOL_CALLS` | 回合内所有工具调用总量上限 |
  
  缺失 / 空白 / 非法（如 `abc`）/ 非正数（`0`、`-3`）**一律视为不限**——配置手误不该让启动崩掉
  或行为漂移。解析走纯函数 `parseLimit`，可被单测直接盯住。
- **撞限也不杀回合**——`onLimitExceeded(RETURN_ERROR_RESPONSE)`：错误文本作为该次调用的
  tool 结果回给模型（框架在两种模式下都会先填充 `ToolResponseMessage`，THROW 只是**额外**再抛
  异常），由模型自行收敛：换 `Write` 整写、改用别的工具、或收尾汇报。
  **错误是模型的输入，不是回合的死刑**——与 Resilient 系列同一哲学。
- 保留 Resilient 容错包装（工具名解析失败 + 工具执行异常转错误文本），主/子 agent 一并继承。

### 配置后的行为对比

| | 修复前（框架默认 THROW） | 修复后 |
| --- | --- | --- |
| 默认状态 | 40 次即拦，杀整回合 | **完全不限** |
| 配置了限额且撞限 | `ToolCallLimitExceededException` 裸抛，回合报废 | 错误文本回给模型，工具不执行，**回合继续** |
| 子 agent | 同框架裸默认，且无任何 Resilient 防线 | 与主 agent 同源（限额 + 容错） |

## 实测验证（生产进程内）

修复后的发行包（1.21.7）在真实会话中做了一次**越线压测**：让模型在**同一回合内连续调用
`Bash` 工具 50 次**（累计 51 次，远超旧默认的 40 次硬线）。

| 项 | 结果 |
| --- | --- |
| 运行进程 | `~/springai-code-tui-1.21.7/springai-code-tui.jar`（lib 含 `spring-ai-model-2.0.1.jar`） |
| 本回合 `Bash` 调用次数 | 51 |
| 被拦截次数 | **0** |
| 日志旁证 | `~/springai-code-tui-1.21.7/logs/springai-code-tui.log` 中 `Tool call limit` / `exceeded for tool` 零命中 |

关键在于**这不只是「没报错」**：旧默认是 `THROW`，撞限会在第 41 次当场抛出异常杀掉整个回合，
根本不会有后续输出。一路跑到 51 次并正常收尾，本身就是「回合存活」的证据。

## 验证

- `mvn -pl springai-code-tui -am clean test`：inline-patch 75 项、code-tui 2107 项测试
  无失败、无错误（跳过 13 项为门控冒烟）。
- 新增 `TurnToolLimitWiringTest` 6 项：默认不限的任意深度执行、配置后撞限回错误文本且工具不执行、
  临界值（含上限）正常执行、总量限生效、`parseLimit` 纯函数（缺失/空白/非法/非正数一律不限）、
  **框架默认裸行为的 characterization 对照组**（钉住「我们在逃离什么」，Spring AI 默认值漂移时
  该用例先红，提醒复核策略）。
  RED 阶段确认用例因 `TurnToolLimitWiring` 不存在而编译失败后才实现。
- 发布包解包核验：主 jar 含 `TurnToolLimitWiring.class`，`bin/config.env.example` 含两个新变量。
